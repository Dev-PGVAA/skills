# Deep Research

Your purpose is to reduce uncertainty.

Search before reasoning whenever current external information can materially
change the answer.

Do not research merely to decorate the response with citations.

Research the assumptions that determine the decision.

---

# Evidence Stack

Knowledge has two dimensions:

1. SOURCE QUALITY
2. RECENCY / RELEVANCE

---

# Knowledge Levels

## LEVEL A — Primary / authoritative

Examples:

- official documentation
- official company documentation
- Harvard / HBS / HarvardX
- peer-reviewed papers
- standards
- government datasets
- SEC filings
- source code
- official APIs
- technical specifications

Use as strongest evidence.

---

## LEVEL B — Established frameworks

Examples:

- respected books
- established academic frameworks
- widely validated business frameworks
- recognized technical literature

Strong for models and mental frameworks.

Potentially weaker for current facts.

---

## LEVEL C — Credible cases

Examples:

- company case studies
- engineering blogs
- documented startup cases
- postmortems
- technical case reports

Useful for real-world implementation evidence.

---

## LEVEL D — Operator / creator knowledge

Examples:

- founders
- practitioners
- creators
- marketers
- growth operators
- Telegram channels
- Twitter/X threads
- YouTube
- podcasts

Useful for tactics and emerging patterns.

Must not automatically be treated as universal truth.

---

## LEVEL E — Anecdotal

Examples:

- individual claims
- screenshots
- revenue claims
- unverified anecdotes
- isolated observations
- viral posts

Treat as hypothesis-generating evidence only.

---

# Dynamic Search & Research Layer

Search is NOT Level F.

Search is a mechanism that can discover evidence at ANY level.

Example:

Search → official Stripe documentation = Level A.

Search → HBS study = Level A.

Search → respected engineering postmortem = Level C.

Search → creator TikTok = Level D/E.

Always classify discovered evidence.

---

# Search strategy

Before searching create an uncertainty map.

Example:

UNKNOWN:
- actual competitors
- API restrictions
- price
- market demand
- technical feasibility

KNOWN:
- user goal
- target platform

Search unknowns with the highest:

IMPACT × UNCERTAINTY.

---

# Query decomposition

Use multiple independent queries.

Example:

Topic:
AI meeting assistant for lawyers.

Research separately:

1. existing products
2. legal privacy requirements
3. transcription API economics
4. willingness to pay
5. complaints about existing tools
6. security requirements
7. workflow integration
8. market adoption

Do not use one giant query.

---

# Triangulation

Important claims should ideally have:

- primary source
and/or
- multiple independent sources.

When sources conflict:

show the disagreement.

Do not average conflicting facts silently.

---

# Recency

For rapidly changing topics prioritize recent evidence:

- AI
- software
- APIs
- pricing
- laws
- cybersecurity
- social platforms
- SEO
- algorithms
- product availability

Older sources may still be used for foundational frameworks.

---

# Research attacks / Contrarian search

Search not only for supporting evidence. **Half the search budget is for killing the claim.**

Also search for:

- failure and shutdowns of analogous products
- complaints, churn reasons, negative reviews
- alternatives and substitutes the user already uses
- limitations, policy restrictions, price increases
- security incidents and trust breaks
- historical parallels that failed for the same structural reason
- data that would force a different recommendation

## Contrarian protocol (when the user challenges a conclusion, or product/evaluate needs counter-evidence)

1. State the claim to be tested in one sentence.
2. Write 3–5 **disconfirming hypotheses** (“this fails because…”).
3. Search each hypothesis independently (do not reuse the supporting-evidence query).
4. Rank what you find by source level (A–E) and impact on the decision.
5. Report **what would change the conclusion** with a concrete threshold, not a vague caveat.

Research must actively attempt falsification. A report with only confirming sources is incomplete.

# Competitor research

For each important competitor determine:

WHO
TARGET USER
POSITIONING
FEATURES
PRICE
DISTRIBUTION
STRENGTH
WEAKNESS
COMPLAINTS
DIFFERENTIATION

Avoid feature-list-only competitive analysis.

---

# Technical research

Prefer:

1. official docs
2. specifications
3. repositories
4. primary papers
5. maintainers

Search developer communities primarily for:

- bugs
- undocumented limitations
- adoption friction
- production experience
